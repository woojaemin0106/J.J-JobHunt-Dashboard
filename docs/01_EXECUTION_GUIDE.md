## EG-01 실행 원칙

### 정의
- 팀이 실제 구현을 진행할 때 지켜야 하는 운영 원칙을 정의한다.

### 현재 상태
- 기준선 시점에 정책 문서가 새로 정립되었고, 코드 품질 게이트는 완전 자동화되지 않았다.

### 앞으로의 원칙
- 문서 우선: 구현 전 작업 목적/범위/완료조건을 MUST 문서화한다.
- 작은 단위 배포: 변경은 리뷰 가능한 크기로 SHOULD 분할한다.
- 회귀 방지 우선: 신규 기능보다 기존 핵심 여정 안정화를 MUST 우선한다.
- 근거 기반 결정: 성능/구조 변경은 측정/사실 근거를 SHOULD 동반한다.

### 검증 기준
- [ ] 모든 작업에 정책 ID와 완료조건이 있다.
- [ ] 큰 변경은 2개 이상 PR로 분할된다.
- [ ] 핵심 여정 회귀 테스트가 PR마다 수행된다.

## EG-02 작업 단위 템플릿

### 정의
- 구현 담당자가 작업을 시작할 때 사용하는 표준 작업 카드 형식을 정의한다.

### 현재 상태
- 작업 기록 형식이 개인별로 달라 리뷰 일관성이 낮았다.

### 앞으로의 원칙
- 아래 템플릿을 MUST 사용한다.

```md
# EG-TASK-YYYYMMDD-##

- 제목:
- 연결 정책 ID: BP-__
- 담당자:
- 우선순위: P0 | P1 | P2

## 배경
- 어떤 사용자 문제를 해결하는가:

## 작업 내용
- 구현 범위:
- 비범위:

## 영향 범위
- 사용자 영향:
- 데이터 영향:
- 운영 영향:

## 완료 조건 (DoD)
- [ ] 코드 변경 완료
- [ ] 테스트 통과
- [ ] 문서 반영
- [ ] 리뷰 승인

## 검증 방법
- 자동 검증:
- 수동 시나리오:
```

- 템플릿 없는 작업 착수는 금지한다.

### 검증 기준
- [ ] 백로그 카드 100%가 템플릿 필드를 채운다.
- [ ] 모든 카드에 `연결 정책 ID`가 존재한다.
- [ ] 완료된 카드에 검증 결과가 남아 있다.

## EG-03 게이트형 초기 단계 (Gate 0~3)

### 정의
- 프로젝트 재시작 초기에 반드시 순차 통과해야 하는 단계별 완료 조건을 정의한다.

### 현재 상태
- 기준선 시점 상태:
  - 실행/빌드 가능
  - lint 에러 존재
  - 인증/데이터 경계 규칙 불완전
  - CI 품질 게이트 미도입

### 앞으로의 원칙
- Gate는 순차 통과를 MUST 따른다. (건너뛰기 금지)

1. Gate 0 (기준선)
- 목표: 실행/빌드/린트/환경 변수 문서화 완료.
- 산출물:
  - 실행 명령, 빌드 명령, 린트 명령 결과 기록
  - 필수 환경변수 목록 및 설명
  - 현재 known issues 목록

2. Gate 1 (품질 안정화)
- 목표: lint 에러 0, 타입 에러 0, 핵심 플로우 수동 테스트 통과.
- 산출물:
  - lint/build 결과 캡처 또는 로그
  - 핵심 플로우 테스트 체크리스트 완료

3. Gate 2 (경계 확립)
- 목표: 인증 경계, 데이터 경계, 에러 핸들링 기준 적용.
- 산출물:
  - 공개/보호 라우트 규칙 반영
  - 저장 키/스코프 정책 반영
  - 사용자 메시지/로그 정책 반영

4. Gate 3 (운영 준비)
- 목표: CI, PR 품질 게이트, 릴리즈/롤백 절차 확정.
- 산출물:
  - CI 파이프라인(최소 lint/build)
  - PR 승인 체크리스트 강제
  - 릴리즈 런북/롤백 런북 확정

### 검증 기준
- [ ] Gate별 진입/종료 조건이 명확히 기록된다.
- [ ] Gate 종료 시점에 산출물이 저장소 문서로 남는다.
- [ ] 선행 Gate 미통과 상태에서 후속 Gate 작업이 진행되지 않는다.

## EG-04 칸반 전환 기준

### 정의
- 게이트 단계를 통과한 이후 연속 개선 운영(칸반)으로 전환하는 기준을 정의한다.

### 현재 상태
- 재시작 초기 단계이며, 작업 흐름은 게이트형 운영이 적합하다.

### 앞으로의 원칙
- 전환 조건:
  - Gate 0~3 완료 후 칸반으로 MUST 전환한다.
- 칸반 운영 규칙:
  - WIP 제한: 진행 중 항목 최대 3개.
  - 우선순위: 사용자 영향도 > 회귀 위험도 > 구현 비용.
  - 카드 완료 조건: 구현 + 테스트 + 문서 반영 + 리뷰 승인.
- 긴급 이슈(P0)는 WIP 제한 예외를 MAY 허용하되 사유를 기록한다.

### 검증 기준
- [ ] 칸반 보드에 WIP 초과 항목이 없다.
- [ ] 우선순위 근거가 카드에 기록된다.
- [ ] 완료 카드에는 테스트/문서/리뷰 근거가 존재한다.

## EG-05 테스트 매트릭스

### 정의
- 단위/통합/수동 테스트 범위를 표준화해 품질 회귀를 방지한다.

### 현재 상태
- 일부 수동 테스트 경험은 있으나 테스트 매트릭스가 문서화되어 있지 않았다.

### 앞으로의 원칙
- 테스트 매트릭스는 아래 기준을 MUST 따른다.

| 범주 | 대상 | 필수 시나리오 |
|---|---|---|
| 단위 | 순수 유틸/상태 전환 로직 | 날짜 계산, ID 생성, reducer 전이 |
| 통합 | 라우트+스토어+UI 연결 | 인증 상태별 라우트 접근, CRUD 반영 |
| 수동 | 핵심 사용자 여정 | 로그인, 지원 CRUD, 메모 CRUD, 할일 CRUD, 통계 조회 |

- 회귀 방지 핵심 시나리오:
  - 인증 성공/실패/로그아웃
  - 지원 추가/수정/상태 변경/삭제
  - 이력서 버전 추가/삭제
  - 메모 추가/편집/삭제
  - 할 일 추가/토글/삭제
  - 통계 화면 값 반영 확인

### 검증 기준
- [ ] PR마다 영향 범위에 맞는 테스트 범주가 선택된다.
- [ ] 핵심 여정 수동 시나리오 결과가 기록된다.
- [ ] 회귀 버그 발생 시 해당 시나리오가 매트릭스에 즉시 반영된다.

## EG-06 PR 리뷰 가이드

### 정의
- 리뷰어가 품질/리스크를 같은 기준으로 판단할 수 있는 규칙을 정의한다.

### 현재 상태
- PR 템플릿은 있으나 차단 기준과 승인 기준이 문서로 고정되어 있지 않았다.

### 앞으로의 원칙
- PR 필수 체크:
  - 목적/변경 이유
  - 테스트 방법 및 결과
  - 정책 ID(BP-xx) 참조
  - 리스크 및 롤백 관점
- 차단 조건(Blocker):
  - lint/build 실패
  - 핵심 여정 회귀 가능성 미검증
  - 정책 문서와 충돌하는 구현
- 승인 기준:
  - 문제 정의와 구현이 일치
  - 테스트 근거 충분
  - 운영 리스크와 후속 작업이 명확

### 검증 기준
- [ ] 모든 PR이 필수 체크 항목을 충족한다.
- [ ] 차단 조건 발생 PR은 merge되지 않는다.
- [ ] 승인 코멘트에 최소 1개의 품질 근거가 포함된다.

## EG-07 릴리즈 체크리스트

### 정의
- 배포 전/중/후 수행해야 할 점검과 롤백 트리거를 정의한다.

### 현재 상태
- 릴리즈 절차가 팀 공통 문서로 정리되어 있지 않다.

### 앞으로의 원칙
- 사전 점검(Pre-release):
  - 린트/빌드 통과
  - 핵심 여정 수동 테스트 통과
  - 환경변수/설정 검증
- 배포(Release):
  - 배포 커밋/태그 기록
  - 변경 요약 공지
- 사후 확인(Post-release):
  - 인증 동작 확인
  - 핵심 CRUD 확인
  - 콘솔 오류/성능 저하 확인
- 롤백 트리거:
  - 로그인 불가
  - 데이터 손실/오염
  - 핵심 여정 실패율 급증

### 검증 기준
- [ ] 릴리즈마다 사전/사후 체크 기록이 남는다.
- [ ] 롤백 트리거 발생 시 30분 내 의사결정 로그가 남는다.
- [ ] 릴리즈 노트와 실제 배포 내용이 일치한다.

## EG-08 운영 루틴

### 정의
- 데일리/주간/회고/문서 갱신 루틴을 표준화해 운영 품질을 유지한다.

### 현재 상태
- 루틴이 사람 의존적이며 문서 갱신 책임이 명확하지 않다.

### 앞으로의 원칙
- 데일리(매일):
  - 어제/오늘/리스크 공유
  - WIP 점검 및 재조정
- 주간 리뷰(매주):
  - KPI 변화 점검
  - Gate 또는 칸반 진행률 점검
  - 리스크 레지스터 갱신
- 회고(격주 또는 월간):
  - 재발 이슈 분석
  - 정책/실행 문서 개선안 도출
- 문서 갱신:
  - 작업 작성자가 1차 반영 MUST
  - 리뷰어가 2차 검증 SHOULD

### 검증 기준
- [ ] 데일리/주간/회고 기록이 누락 없이 보관된다.
- [ ] 리스크 항목이 주간 단위로 최신화된다.
- [ ] 문서 버전이 실제 운영 변경을 반영한다.

## EG-09 이슈 처리 런북

### 정의
- 주요 장애 유형별 탐지-진단-복구-재발방지 절차를 정의한다.

### 현재 상태
- 장애 대응이 경험 의존적이며 표준 절차가 부족하다.

### 앞으로의 원칙
- 공통 절차:
  - 탐지: 증상 확인, 영향 범위 파악
  - 진단: 원인 후보 1~3개 수집
  - 복구: 즉시 완화 조치 우선
  - 재발방지: 근본 원인 수정 + 문서 반영
- 유형별 기본 대응:
  1. 인증 실패
     - 세션 상태 확인, 환경변수 확인, 라우트 경계 확인
  2. 데이터 손실
     - 저장 키/스코프 확인, 직전 배포 비교, 백업 경로 확인
  3. 빌드 실패
     - 최근 변경 범위 격리, 타입/린트 로그 기준 복구
  4. 성능 저하
     - 프로파일링, 최근 렌더링 변경 분석, 임시 완화 적용

### 검증 기준
- [ ] 장애 티켓에 공통 절차 4단계 기록이 있다.
- [ ] 재발 이슈는 대응 문서가 업데이트된다.
- [ ] 유형별 런북을 기준으로 신규 담당자도 대응 가능하다.

## EG-10 온보딩 체크리스트

### 정의
- 신규 참여자가 첫날부터 첫 PR 완료까지 필요한 최소 경로를 정의한다.

### 현재 상태
- 구두 전달 비중이 높아 신규 참여자 온보딩 시간이 길어질 수 있다.

### 앞으로의 원칙
- Day 1:
  - 저장소 실행/빌드/린트 확인
  - 정책 문서(BP)와 실행 문서(EG) 읽기
  - 핵심 여정 수동 실행
- Day 2~3:
  - 작은 범위 작업 카드 1개 수행
  - 정책 ID 참조 포함 PR 작성
- First PR:
  - 테스트 근거 제출
  - 문서 반영 완료
  - 리뷰 피드백 반영 후 머지
- 온보딩 목표:
  - 3영업일 내 첫 PR merged를 SHOULD 목표로 한다.

### 검증 기준
- [ ] 신규 참여자 첫 PR에 정책 ID 참조가 포함된다.
- [ ] 첫 PR에서 테스트/문서/리뷰 기준이 충족된다.
- [ ] 온보딩 종료 후 개선 피드백이 문서에 반영된다.
