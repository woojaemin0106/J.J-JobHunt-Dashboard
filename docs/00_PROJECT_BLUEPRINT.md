## BP-01 프로젝트 차터

### 정의
- 본 프로젝트는 취업 준비 활동(지원, 이력서 버전, 메모, 할 일, 통계)을 한 화면 체계에서 관리하는 웹앱이다.
- 본 섹션은 왜 이 제품을 운영하는지, 무엇을 성공으로 보는지, 무엇을 당장 하지 않는지를 정의한다.

### 현재 상태
- 프론트엔드 스택은 React + TypeScript + Vite + TailwindCSS이다.
- 인증은 Supabase Auth를 사용하나 핵심 도메인 데이터는 브라우저 `localStorage` 기반이다.
- 빌드는 통과하지만 린트는 실패 상태(기준선 시점)이며 CI 품질 게이트가 없다.
- 문서 중심 실행 규칙이 부재하여 구현/리뷰 판단 기준이 사람마다 다를 수 있다.

### 앞으로의 원칙
- 팀은 문서 우선 실행을 MUST 따른다.
- 목표는 “재현 가능한 실행”이며, 특정 개인의 암묵지 의존을 SHOULD 제거한다.
- 성공은 기능 추가량이 아니라 사용자 준비 효율 개선으로 측정해야 한다.
- 비목표: Gate 0~1에서 전면 재설계/대규모 리브랜딩/다중 역할 권한 체계는 WON’T 포함한다.

### 검증 기준
- [ ] 목표/성공/비목표 문장이 PR/이슈 템플릿과 충돌하지 않는다.
- [ ] 신규 참여자가 10분 내 프로젝트 목적과 경계를 설명할 수 있다.
- [ ] 우선순위 논쟁 시 본 섹션 근거로 결정이 가능하다.

## BP-02 사용자 정의

### 정의
- 핵심 사용자와 보조 사용자를 구분하고, 사용 맥락(언제/왜/어디서 사용하는지)을 정의한다.

### 현재 상태
- 1차 사용자는 취업 준비를 진행 중인 개인이며, 데스크톱 중심 사용 패턴이 예상된다.
- 보조 사용자는 멘토/리뷰어(이력서/지원 현황 피드백 제공자)이나 읽기/공유 기능은 아직 제한적이다.

### 앞으로의 원칙
- 핵심 사용자(Primary Persona)는 “지원 파이프라인을 주 단위로 운영하는 구직자”로 MUST 고정한다.
- 보조 사용자(Secondary Persona)는 “이력서/전략 리뷰를 돕는 외부 조력자”로 SHOULD 정의한다.
- 모바일은 참고/확인, 데스크톱은 작성/편집 중심으로 MAY 최적화한다.
- 주요 UX 판단은 “이번 주에 무엇을 해야 하는지 명확해지는가?”를 기준으로 MUST 평가한다.

### 검증 기준
- [ ] 모든 신규 기능 요구는 Primary Persona 문제와 직접 연결된다.
- [ ] 보조 사용자 시나리오는 공유/리뷰 지원 요구가 있을 때만 범위에 포함된다.
- [ ] 사용 맥락(데스크톱/모바일)별 최소 1개 시나리오가 테스트에 포함된다.

## BP-03 핵심 사용자 여정

### 정의
- 로그인, 지원 관리, 이력서 버전 관리, 메모, 통계 확인까지의 핵심 흐름을 정의한다.

### 현재 상태
- `/login`, `/signup` 화면은 존재한다.
- 지원/이력서/메모/통계 페이지 기능은 존재하나 라우트 보호 정책은 명시적이지 않다.
- 여정 간 데이터 연계(예: 통계와 실제 액션 연결)는 제한적이다.

### 앞으로의 원칙
- 여정 1(인증): 로그인 성공 시 메인 대시보드 진입, 실패 시 사용자 친화 메시지를 MUST 제공한다.
- 여정 2(지원 관리): 지원 추가/수정/단계 이동/조회 흐름을 MUST 제공한다.
- 여정 3(이력서 버전): 지원 항목별 버전 생성/수정/삭제 이력을 SHOULD 명확히 표현한다.
- 여정 4(메모): 빠른 기록과 편집, 삭제 보호(확인 절차)를 MUST 보장한다.
- 여정 5(통계): 사용자가 다음 행동을 결정할 수 있는 지표를 SHOULD 제공한다.

### 검증 기준
- [ ] 핵심 여정 5개에 대해 시작 조건/종료 조건이 문서화되어 있다.
- [ ] 여정별 실패 경로(인증 실패, 저장 실패)가 최소 1개 이상 정의되어 있다.
- [ ] 수동 테스트에서 여정 5개가 모두 통과한다.

## BP-04 문제-해결 매핑

### 정의
- 사용자 문제를 기능으로 직접 매핑해 “무엇을 왜 만드는지”를 명확히 한다.

### 현재 상태
- 기능은 있으나 문제-해결 관계가 문서화되어 있지 않아 우선순위 판단이 어렵다.

### 앞으로의 원칙
- 기능 제안은 반드시 아래 매핑 중 하나와 연결되어야 MUST 한다.

| 사용자 문제 | 해결 방식(현재/목표) | 성공 신호 |
|---|---|---|
| 지원 마감/단계 누락 | 칸반 + D-day + 주간 우선 작업 | 마감 놓침 건수 감소 |
| 회사별 이력서 관리 어려움 | 지원별 버전 기록 | 버전 생성 빈도 증가 |
| 준비 내용 흩어짐 | 메모 + 할 일 통합 | 주간 완료율 증가 |
| 현재 상태 파악 어려움 | 통계 요약 카드 | 다음 행동 결정 시간 감소 |
| 인증/세션 혼란 | 명확한 인증 경계와 오류 메시지 | 인증 이슈 재발 감소 |

### 검증 기준
- [ ] 신규 이슈는 “문제 문장”과 “해결 문장”을 1:1로 포함한다.
- [ ] 해결 방식이 KPI( BP-05 )와 연결된다.
- [ ] 구현 완료 후 성공 신호를 수동/자동으로 측정한다.

## BP-05 KPI 트리

### 정의
- 제품 효과를 측정하기 위한 북극성 지표와 보조 지표, 측정 주기/목표값을 정의한다.

### 현재 상태
- 기준선 시점에는 이벤트 계측이 없으며 정량 KPI 자동 수집이 불가능하다.
- 통계 페이지는 존재하지만 운영 KPI로 직접 쓰기엔 구조화가 부족하다.

### 앞으로의 원칙
- 북극성 지표(NSM): `주간 의미 있는 준비 액션 수(Weekly Meaningful Prep Actions)`.
- 보조 지표는 아래 5개를 SHOULD 사용한다.
  - `S1`: 주간 지원 업데이트가 1회 이상인 사용자 비율
  - `S2`: 지원 1건당 이력서 버전 생성 수
  - `S3`: 주간 할 일 완료율
  - `S4`: 마감 임박(7일 이내) 항목 처리율
  - `S5`: 인증 실패 후 복구 성공률
- 측정 주기: 주간 리뷰 MUST, 월간 회고 SHOULD.
- 기준값은 Gate 0에서 수동 측정으로 수집하고, 목표값은 Gate 2 종료 시 재설정한다.

### 검증 기준
- [ ] NSM 1개 + 보조 지표 3~5개가 문서와 운영 회의록에 일치한다.
- [ ] 각 지표에 측정 책임자와 측정 주기가 지정되어 있다.
- [ ] 주간 리뷰에서 지표 변화와 작업 우선순위가 연결된다.

## BP-06 범위 정책

### 정의
- Must/Should/Could/Won’t 프레임으로 현재 릴리즈에서 무엇을 반드시/가능하면/보류할지 정의한다.

### 현재 상태
- 범위 경계 문서가 없어 “좋아 보이는 일”이 우선되는 위험이 존재한다.

### 앞으로의 원칙

| 분류 | 항목 |
|---|---|
| Must | 문서 우선 프로세스, lint/build 기준선 확립, 핵심 여정 회귀 방지, 인증/데이터 경계 명문화 |
| Should | CI 품질 게이트, 문구/접근성 정비, 수동 테스트 시나리오 체계화 |
| Could | 통계 시각화 확장, 공유/내보내기, 고급 검색/필터 |
| Won’t (현재 단계) | 다중 사용자 협업 편집, 대규모 백엔드 재설계, 복잡한 RBAC |

- Must 항목은 일정 압박이 있어도 제외할 수 없다.
- Won’t 항목은 근거 없는 예외 적용을 금지한다.

### 검증 기준
- [ ] 모든 작업은 MoSCoW 분류를 갖는다.
- [ ] 스프린트 종료 시 Must 미완료 항목이 없거나, 공식 리스크 승인 기록이 있다.
- [ ] Won’t 항목이 무단으로 백로그에 재유입되지 않는다.

## BP-07 도메인 모델

### 정의
- `Application`, `ResumeVersion`, `Note`, `Todo`, `AuthState`의 책임/관계/계약을 정의한다.

### 현재 상태
- 타입은 코드에 존재하나, 필드 의미/nullable 규칙/관계 규약이 문서화되지 않았다.

### 앞으로의 원칙
- 데이터 스키마 계약(공개 계약)은 아래를 MUST 따른다.

| 타입 | 필드 | 필수 여부 | 규칙 |
|---|---|---|---|
| Application | `id` | 필수 | 전역 또는 사용자 범위 내 고유 문자열 |
| Application | `companyName`, `jobTitle` | 필수 | 공백 문자열 금지 |
| Application | `status` | 필수 | `writing`/`submitted`/`passed`/`failed` 중 하나 |
| Application | `deadline` | 필수(문자열) | 미설정은 빈 문자열(`""`) 허용 |
| Application | `versions` | 필수 | `ResumeVersion[]`, 기본값 빈 배열 |
| Application | `createdAt` | 필수 | ISO-8601 문자열 |
| ResumeVersion | `id`, `versionName`, `content`, `updatedAt` | 필수 | `updatedAt`은 ISO-8601 |
| Note | `id`, `title`, `content`, `createdAt`, `updatedAt` | 필수 | 수정 시 `updatedAt` 갱신 |
| Todo | `id`, `text`, `completed`, `createdAt` | 필수 | 완료 토글 시 `completedAt` 갱신 |
| Todo | `completedAt` | 선택 | `completed=true`면 SHOULD 존재 |
| AuthState | `user`, `isAuthenticated`, `isLoading` | 필수 | 상태 전이 규칙은 BP-09 따름 |

- 관계 규칙:
  - `Application` 1개는 `ResumeVersion` 0..N개를 가진다.
  - `Note`, `Todo`는 독립 리소스이며 `Application`과 직접 FK를 강제하지 않는다(v1).

### 검증 기준
- [ ] 타입별 필드 규칙이 코드 타입과 모순되지 않는다.
- [ ] 입력/수정 처리에서 필수 필드 누락이 차단된다.
- [ ] 상태 전이 및 관계 규칙이 수동 테스트에서 확인된다.

## BP-08 상태/데이터 정책

### 정의
- 로컬 저장, 원격 저장, 캐시, 마이그레이션, 키 네이밍 규칙을 정의한다.

### 현재 상태
- 핵심 데이터는 `localStorage`에 저장되며 키는 정적 네이밍(`jj_jobhunt_*_v1`)이다.
- 애플리케이션 초기화 시 저장 데이터가 없으면 mock 데이터로 채워진다.
- 사용자 단위 분리 정책과 키 버전 마이그레이션 절차가 미정이다.

### 앞으로의 원칙
- 저장소 키 네이밍 계약:
  - 형식: `jj.jobhunt.{resource}.v{n}.{scope}`
  - `resource`는 `applications`/`notes`/`todos` 중 하나를 MUST 사용한다.
  - `scope`는 기본적으로 `user:{userId}`를 SHOULD 사용한다.
- 로컬/원격 정책:
  - Gate 0~1: 로컬 저장 안정화 MUST.
  - Gate 2 이후: 원격 저장 전환 여부를 ADR로 결정 SHOULD.
- 캐시 정책:
  - 파생 계산값은 `useMemo` 등 UI 레벨 캐시를 MAY 사용한다.
  - 영속 캐시는 데이터 일관성을 해치지 않도록 버전 태그를 MUST 포함한다.
- 마이그레이션 원칙:
  - 저장 키/스키마 변경 시 “읽기-변환-저장-백업 삭제” 단계 정의를 MUST 문서화한다.

### 검증 기준
- [ ] 저장 키가 네이밍 계약을 따른다.
- [ ] 로그인 사용자 전환 시 데이터 스코프 충돌이 없다.
- [ ] 스키마 변경 PR에는 마이그레이션 테스트 절차가 포함된다.

## BP-09 인증/권한 정책

### 정의
- 로그인 상태별 접근 규칙, 공개/보호 라우트, 리다이렉트, 인증 상태 전이를 정의한다.

### 현재 상태
- 로그인/회원가입 화면은 존재하나 보호 라우트 정책이 명확히 적용되지 않았다.
- 인증 컨텍스트 중복 마운트 위험이 있으며 인증 실패 메시지 표준이 부족하다.

### 앞으로의 원칙
- 라우트 접근 계약:
  - 공개 라우트: `/login`, `/signup`
  - 보호 라우트: `/`, `/applications`, `/resume`, `/notes`, `/statistics`
  - 비인증 사용자가 보호 라우트 진입 시 `/login`으로 MUST 리다이렉트한다.
  - 인증 사용자가 `/login` 또는 `/signup` 접근 시 `/`로 SHOULD 리다이렉트한다.
- 인증 상태 인터페이스 계약:
  - `isLoading=true`: 세션 확인 중(권한 판단 보류).
  - `isAuthenticated=true`: 유효 사용자 세션 존재.
  - `user=null`이면 `isAuthenticated=false`를 MUST 유지한다.
- 권한 수준은 v1에서 단일 사용자 권한 모델로 고정한다.

### 검증 기준
- [ ] 공개/보호 라우트 정책이 라우터 구현과 일치한다.
- [ ] 로그인/로그아웃/세션 만료 시 상태 전이가 정의대로 동작한다.
- [ ] 인증 실패 메시지가 사용자에게 안전하고 명확하다.

## BP-10 UI/UX 정책

### 정의
- 디자인 톤, 접근성 기준, 반응형 기준, 문구 정책을 정의한다.

### 현재 상태
- 공통 UI 유틸 클래스가 존재하며 카드/버튼/입력 패턴이 어느 정도 통일되어 있다.
- 페이지별 문구/상호작용 일관성은 일부 개선 여지가 있다.

### 앞으로의 원칙
- 디자인 톤:
  - 명확한 정보 밀도 + 행동 유도 중심 인터페이스를 MUST 유지한다.
  - 시각 효과는 정보 가독성을 해치지 않는 선에서 SHOULD 사용한다.
- 접근성:
  - 키보드 접근, 포커스 표시, 라벨 연결을 MUST 보장한다.
  - 색상만으로 상태를 전달하지 않도록 SHOULD 구성한다.
- 반응형:
  - 모바일(<=768), 태블릿, 데스크톱 구간에서 레이아웃 깨짐이 없어야 MUST 한다.
- 문구:
  - 행동 지향 문구(무엇을 해야 하는지)와 오류 복구 문구(다음 행동)가 SHOULD 포함된다.

### 검증 기준
- [ ] 핵심 화면에서 키보드만으로 주요 동작이 가능하다.
- [ ] 모바일/데스크톱에서 핵심 여정 UI 깨짐이 없다.
- [ ] 오류/성공 메시지가 “원인+다음 행동”을 포함한다.

## BP-11 성능 기준

### 정의
- 초기 로딩, 상호작용 응답성, 리렌더링, 번들 크기에 대한 기준과 예산을 정의한다.

### 현재 상태
- 렌더링 최적화 작업이 진행되었으나 측정 절차 표준이 미약하다.
- build 산출 기준 대략 440KB JS 수준(기준선 시점)이며 체계적 예산은 없다.

### 앞으로의 원칙
- 성능 예산(초기 기준):
  - 프로덕션 JS 번들 gzip 150KB 내외를 SHOULD 목표로 하되 초과 시 원인 분석 MUST.
  - 주요 상호작용(카드 클릭/메모 수정/할 일 토글)은 체감 지연 100ms 이하를 SHOULD 목표로 한다.
- 렌더링 정책:
  - 파생 연산은 `useMemo`, 콜백 참조 안정화는 `useCallback`을 MAY 사용한다.
  - 최적화는 측정 근거가 있을 때만 MUST 적용한다.
- 측정 정책:
  - DevTools/React Profiler로 회귀 확인을 SHOULD 수행한다.

### 검증 기준
- [ ] 성능 관련 PR에 “측정 전/후” 근거가 포함된다.
- [ ] 핵심 상호작용에서 불필요한 전체 리렌더가 발생하지 않는다.
- [ ] 번들 급증 시 원인/대응 기록이 남는다.

## BP-12 보안/개인정보 정책

### 정의
- 비밀값 관리, 로그 정책, 브라우저 저장 제한, 오류 처리 계약을 정의한다.

### 현재 상태
- `.env`는 git 추적 대상이 아니지만 `.env.example`이 없어 온보딩 리스크가 있다.
- 콘솔 로그 사용 규칙과 민감 정보 마스킹 기준이 명확하지 않다.

### 앞으로의 원칙
- 환경변수 계약:
  - 필수 키: `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`
  - 누락 시 앱은 안전한 실패 동작(명시적 경고 + 기능 제한)을 MUST 제공한다.
  - 로컬/배포 환경 값은 서로 분리 MUST.
- 오류 처리 계약:
  - 사용자 메시지는 복구 가능한 행동 지시를 SHOULD 포함한다.
  - 콘솔 로그는 디버깅 정보만 남기고, 토큰/개인정보 노출을 MUST 금지한다.
- 브라우저 저장 제한:
  - 비밀번호/토큰 원문 저장은 MUST 금지한다.
  - 개인정보 텍스트 저장이 필요한 경우 최소화 SHOULD.

### 검증 기준
- [ ] 필수 환경변수 누락 시 동작이 문서와 일치한다.
- [ ] 로그 점검에서 민감 정보 노출이 없다.
- [ ] 로컬 저장 데이터에 인증 비밀값이 포함되지 않는다.

## BP-13 배포/릴리즈 정책

### 정의
- 브랜치 전략, PR 요건, 배포 조건, 롤백 조건을 정의한다.

### 현재 상태
- 브랜치 전략은 관례적으로 존재하나 자동 품질 게이트(CI)가 없다.
- PR 템플릿은 있으나 강제 적용 체계는 약하다.

### 앞으로의 원칙
- 브랜치 전략:
  - `main`: 릴리즈 안정 브랜치
  - `dev`: 통합 브랜치
  - `feat/*`: 기능 브랜치
- PR 요건:
  - 목적/테스트 방법/체크리스트를 MUST 작성한다.
  - 정책 ID(BP-xx) 참조를 MUST 포함한다.
- 배포 조건:
  - lint/build 통과 + 핵심 수동 시나리오 통과를 MUST 만족한다.
- 롤백 조건:
  - 인증 불능, 데이터 손실, 핵심 여정 실패가 감지되면 즉시 롤백 SHOULD.

### 검증 기준
- [ ] PR마다 정책 ID 참조가 포함된다.
- [ ] 배포 전 체크리스트 수행 기록이 존재한다.
- [ ] 롤백 트리거 발생 시 대응 절차를 재현할 수 있다.

## BP-14 장애/리스크 레지스터

### 정의
- 주요 리스크를 식별하고 영향도, 대응, 오너를 관리한다.

### 현재 상태
- 개별 이슈는 있으나 통합 리스크 레지스터와 오너십 체계가 없다.

### 앞으로의 원칙

| 리스크 | 영향도 | 대응 원칙 | 오너 |
|---|---|---|---|
| 인증 컨텍스트 중복/세션 혼선 | 높음 | 단일 컨텍스트/상태 전이 검증 | FE 오너 |
| 사용자 데이터 스코프 충돌 | 높음 | 저장 키 스코프 분리/마이그레이션 | FE 오너 |
| 린트 실패 누적 | 중간 | Gate 1에서 0건 강제 | FE 오너 |
| CI 부재로 회귀 유입 | 중간 | Gate 3에서 품질 게이트 도입 | FE + 리뷰어 |
| 환경변수 미문서로 온보딩 지연 | 중간 | `.env.example` 및 온보딩 절차 | FE 오너 |
| 성능 회귀 감지 지연 | 중간 | 성능 측정 절차 표준화 | FE 오너 |

- 리스크는 주간 회의에서 MUST 갱신한다.

### 검증 기준
- [ ] 각 리스크에 오너와 상태(열림/완화/해결)가 있다.
- [ ] 고영향 리스크는 대응 기한이 지정되어 있다.
- [ ] 회고 시 신규 리스크가 누락 없이 반영된다.

## BP-15 의사결정 로그(ADR) 템플릿

### 정의
- 아키텍처/정책 변경 결정을 기록하는 표준 템플릿을 정의한다.

### 현재 상태
- 결정 배경과 대안 비교 기록이 체계화되어 있지 않다.

### 앞으로의 원칙
- 아래 템플릿을 MUST 사용한다.

```md
# ADR-YYYYMMDD-<slug>

- 결정일:
- 상태: 제안 | 승인 | 폐기
- 관련 정책 ID: BP-xx

## 배경
- 문제 상황:
- 제약:

## 선택지
1. 옵션 A
2. 옵션 B
3. 옵션 C

## 결정
- 선택한 옵션:
- 선택 이유:

## 영향
- 긍정 영향:
- 부정 영향:
- 후속 작업:
```

- 기능 영향이 큰 설계 변경은 ADR 없이 머지할 수 없다.

### 검증 기준
- [ ] 정책 변경 PR에 ADR 링크가 존재한다.
- [ ] ADR에 대안 비교와 영향 분석이 포함된다.
- [ ] 폐기된 결정도 기록으로 남아 재논쟁을 줄인다.

## BP-16 용어집

### 정의
- 팀 내 공통 용어를 표준화해 커뮤니케이션 비용을 줄인다.

### 현재 상태
- “지원”, “버전”, “완료”, “게이트” 등의 의미가 문맥마다 다르게 쓰일 여지가 있다.

### 앞으로의 원칙
- 용어는 아래 정의를 SHOULD 기본으로 사용한다.
  - `지원`: 회사/직무 단위의 지원 엔트리(Application)
  - `버전`: 특정 지원에 대응하는 이력서 버전(ResumeVersion)
  - `활성 지원`: `writing` 또는 `submitted` 상태 지원
  - `핵심 여정`: 로그인, 지원 관리, 이력서 버전, 메모, 통계의 5개 흐름
  - `게이트`: 다음 단계로 넘어가기 위한 완료 조건 집합
  - `회귀`: 기존에 동작하던 기능이 깨지는 현상
  - `SSOT`: 정책의 단일 진실원 문서
- 신규 용어 추가는 본 섹션 업데이트를 MUST 동반한다.

### 검증 기준
- [ ] PR/이슈에서 용어 사용이 용어집 정의와 일치한다.
- [ ] 신규 참여자가 용어집만으로 대화 맥락을 이해할 수 있다.
- [ ] 분기별로 용어집이 실제 사용 언어와 동기화된다.
